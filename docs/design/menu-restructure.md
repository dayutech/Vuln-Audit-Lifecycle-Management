# 侧边栏菜单重组方案（t191，待批准）

> 目标读者：产品负责人。本文只描述**信息架构调整**，不含代码改动；批准后再实施。
> 涉及范围：仅前端侧边栏（`frontend/src/layouts/BasicLayout.tsx` + 菜单文案 + 展开态逻辑）。
> 不改 URL、不改接口、不改权限、不改数据库。

## 1. 现状

侧边栏目前是 3 个固定分组（antd `type: 'group'`，分组恒展开，组内平铺）：

| 分组 | 项数 | 成员 |
|---|---|---|
| 核心业务 | 7 | 安全态势大盘、客户管理、项目管理、产品与资产中心、安全审计任务、全局漏洞视图、审批中心 |
| 知识与资源 | 6 | 安全知识库、规范与文档、工具与组件库、**待我处理**、**我发起的**、**生成表单** |
| 系统与管理 | **12** | 团队架构、审批范围、账号管理\*、角色与权限、审计日志\*、数据导入、系统设置†、标签管理†、上传审批†、表单模板†、注册审批\*‡、系统消息 |

\* 仅管理层（admin / project_leader）可见；† 仅管理员可见；‡ 带待审批数量角标。

## 2. 问题

1. **系统与管理已 12 项平铺**，占满一屏，且每项都带图标；新增一个功能就多一行，没有任何收敛机制。
2. **语义混杂**：组织/账号、审批治理、平台配置、表单业务、个人通知混在同一个列表里，扫读成本高。
3. **同一个功能被拆到两个组**：填表系统的「模板管理」在系统与管理，「发起/我发起的/待我处理」在知识与资源。
4. **图标重复**：`AuditOutlined` 同时用于「审批范围」和「注册审批」，`FormOutlined` 同时用于 4 个表单项，视觉上无区分度。

## 3. 目标与约束

**目标**

- 系统与管理由 12 个平铺项 → **4 个子菜单 + 1 个独立项**，每个子菜单 3–4 项。
- 表单相关 4 项收进一个「表单中心」子菜单（含从知识与资源移入的 3 项）。
- 新增功能有明确归位规则 + 数量上限，避免再次无限增长。

**约束**

- URL / 深链 / 书签全部不变（纯信息架构调整）。
- 权限可见性规则不变（管理层 / 管理员 / 全员），角标不变。
- 折叠态侧栏、<lg 窄屏抽屉、中英文案、现有选中态最长前缀匹配全部保持可用。

## 4. 方案 A（推荐）

```
核心业务（不变，7 项）
知识与资源（3 项，移出 3 个表单项）
系统与管理
├─ 组织与账号            （子菜单）
│   ├─ 团队架构            /teams
│   ├─ 账号管理 *          /users
│   ├─ 角色与权限          /roles
│   └─ 注册审批 * ‡        /admin/registration-requests
├─ 审批与合规            （子菜单）
│   ├─ 审批范围            /approval-scopes
│   ├─ 上传审批 †          /admin/upload-approvals
│   └─ 审计日志 *          /audit-logs
├─ 表单中心              （子菜单）
│   ├─ 待我处理            /forms/assigned   ← 自「知识与资源」移入
│   ├─ 我发起的            /forms/mine       ← 自「知识与资源」移入
│   ├─ 生成表单            /forms/new        ← 自「知识与资源」移入
│   └─ 表单模板 †          /admin/form-definitions
├─ 平台设置              （子菜单）
│   ├─ 系统设置 †          /settings
│   ├─ 标签管理 †          /admin/tags
│   └─ 数据导入            /import
└─ 系统消息                /notifications（独立项，未读角标，`BellOutlined`）
```

**要点**

| 项 | 说明 |
|---|---|
| 层级 | 「系统与管理」仍是分组标题；组内 4 个子菜单可折叠 + 1 个独立项 |
| 图标 | 子菜单**父级**各一个图标（`TeamOutlined` / `AuditOutlined` / `FormOutlined` / `ControlOutlined`），**子项不设图标**——消除 4 个重复的 `FormOutlined` 与 2 个重复的 `AuditOutlined`，行高更紧凑 |
| 表单中心顺序 | 按「先处理、再追溯、后创建、最后配置」：待我处理 → 我发起的 → 生成表单 → 表单模板 |
| 可见性 | 子菜单整体隐藏的条件 = 其可见子项为 0（例：工程师看不到「账号管理/审计日志/注册审批」，但「组织与账号」仍有团队架构与角色权限 → 仍显示） |
| 角标 | 注册审批角标、系统消息未读角标逻辑原样保留 |
| 全隐藏时的兜底 | 若某子菜单对当前角色**所有子项**都不可见（例如未来把「平台设置」全设为管理员专属），则该子菜单整项不渲染 |

**为什么这么分**

- **组织与账号**：所有「人 / 角色 / 组织 / 入职审批」相关内容，一个入口。
- **审批与合规**：所有「审批流配置 + 发布审批 + 追溯导出」；新增审批类型（如新的上传审批类别）直接进这里。
- **表单中心**：填表系统全生命周期（模板 → 生成 → 填写/确认 → 导出）集中，避免模板与业务入口分裂。
- **平台设置**：系统级配置与主数据（登录页主题、标签、批量导入）。
- **系统消息**：个人通知，不参与业务分组。

## 5. 增长控制规则（防止再次无限增长）

| 子菜单 | 收什么 | 举例 |
|---|---|---|
| 组织与账号 | 人、角色、组织、注册/入职审批 | 新的审批角色、组织架构同步 |
| 审批与合规 | 审批流配置、各类发布审批、审计追溯与导出 | 新增「知识库发布审批」→ 放这里 |
| 表单中心 | 自定义填表的模板、实例、填写、导出 | 新的填表能力一律进这里 |
| 平台设置 | 系统配置、主数据、批量导入 | 新的字典/枚举管理 → 放这里 |
| 系统消息 | 个人通知（独立项） | — |

- **每个子菜单 ≤ 6 项**；到 6 项时应考虑页内 Tab（如「平台设置」里把标签/行业/项目类型合并成一个「主数据」页），**不得新增顶层分组**。
- 核心业务组保持现状；如需新增顶层分组，走设计评审。

## 6. 交互与实现要点

1. **antd 支持**：v6.3.4 的 `MenuItemGroupType.children` 类型为 `ItemType[]`（包含 `SubMenuType`），「分组内嵌子菜单」类型合法，无需自定义组件。
2. **展开态**：`menuSelection.collectOpenKeys` 已支持非 group 祖先（会返回父级 key），但 `BasicLayout` 目前只在 `openKeys.length > 0` 时受控传入。实施时改为：
   - 受控 `openKeys` + `onOpenChange`；
   - 路由变化时把「当前项所在的子菜单」**并入**已展开集合（不强制关闭用户手动展开的其它子菜单）；
   - 折叠态（`collapsed`）由 antd 自动改为悬浮弹层，无需特殊处理。
3. **选中态**：`collectMenuKeys` 递归收集叶子 key，`/forms/:id`、`/admin/form-definitions/new|:id/edit` 仍按最长前缀匹配落到对应项，无需改动匹配逻辑。
4. **i18n**：新增 4 个键 `menu.groupOrg` / `menu.groupGovernance` / `menu.groupForms` / `menu.groupPlatform`，中英同步（`en-US` 是 `Record<MessageKey, string>`，缺键 `tsc` 会报错）。
5. **折叠/移动端**：侧栏与抽屉共用同一份 `menuItems`，自动一致。
6. **样式**：子菜单内层缩进由 antd 提供；如行高偏松，只需在 `layout.css` 微调，不改结构。

## 7. 不做的事

- 不改任何路由路径、不重定向、不动权限注解。
- 不改「核心业务」顺序（t153 要求：安全审计任务在全局漏洞视图之前）。
- 不合并页面、不改页面内 Tab（本轮只做菜单）。
- 不把「系统消息」搬到顶栏（见待确认项 2）。

## 9. 验收清单

1. 系统与管理下显示 4 个子菜单 + 系统消息独立项；知识与资源仅剩 3 项。
2. 进入任一页面：对应叶子高亮、所属子菜单自动展开；手动展开的其它子菜单不会被强制关闭。
3. 角色矩阵：`admin`（全可见）/ `project_leader`（无 † 项）/ 普通工程师（无 \* 与 † 项）三种视角可见项正确，无空子菜单。
4. 「注册审批」待审批角标、「系统消息」未读角标照常显示。
5. 折叠侧栏（点收起）与 375px 抽屉导航下，子菜单可用、可展开。
6. 中英文切换后 4 个子菜单标题与全部子项文案齐全。
7. `npx tsc -b` 0 错误、`npm run lint` 0 error、`npm run build` 通过；真机（线上）截图核对。

## 11. 已确认的决策（2026-11-25 批准）

| # | 决策 | 结论 |
|---|---|---|
| 1 | 子菜单命名 | **组织与账号 / 审批与合规 / 表单中心 / 平台设置**（按方案 A） |
| 2 | 系统消息位置 | **双入口**：侧栏「系统与管理」末尾保留独立项，另在**顶栏加铃铛**；两处共用同一份未读数，联动刷新 |
| 3 | 子项图标 | **子项不显示图标**，只保留子菜单父级图标 |
| 4 | 「角色与权限」门控 | **一并加上**，按 `managerEligible`（ADMIN + PROJECT_LEADER）门控 |

关于第 4 点的一处事实更正：`RoleController` 的 class-level 注解是
`@PreAuthorize("hasAnyRole('ADMIN','PROJECT_LEADER')")`（读接口对组长开放），只有写操作是 `hasRole('ADMIN')`。
因此门控口径取 `managerEligible` 而不是「仅管理员」——既挡住普通角色点进去吃 403，也不白收走组长的只读入口。
